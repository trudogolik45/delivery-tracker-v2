# Replace Imperative Loop with Event-Driven HOS Scheduler and Policy Object

## Method (The Recipe)

1. Define a `HosPolicy` type that encapsulates all rule constants as a data structure instead of module-level `const` declarations:
   ```ts
   interface HosPolicy {
     avgSpeedMs: number
     maxDriveBeforeBreak: number   // seconds
     breakDuration: number          // seconds
     maxDrivePerShift: number       // seconds
     sleepDuration: number          // seconds (minimum)
     sleepDurationMax: number       // seconds (cap for distributeSlack)
     onDutyWindow: number           // seconds (14 h FMCSA window)
   }
   const DEFAULT_POLICY: HosPolicy = {
     avgSpeedMs: 88_000 / 3600,
     maxDriveBeforeBreak: 8 * 3600,
     breakDuration: 30 * 60,
     maxDrivePerShift: 11 * 3600,
     sleepDuration: 10 * 3600,
     sleepDurationMax: 14 * 3600,
     onDutyWindow: 14 * 3600,
   }
   ```

2. Refactor `simulateMinimum(startedAt, totalDistance, policy)` to accept the policy object. Internally model each shift as a sequence of scheduler events (DriveEvent, BreakEvent, SleepEvent) generated by a stateful scheduler class/function that checks policy limits at each step. The scheduler emits events in order until `dist >= totalDistance`.

3. Refactor `distributeSlack(segments, slack, policy)` to use `policy.sleepDurationMax` and `policy.sleepDuration` instead of hard-coded constants. Apply the same two-phase algorithm (fill headroom, emit tail wait) as in `sleep-cap-tail-wait-block`, but driven by the policy object.

4. `buildTimeline` remains the public API, using `DEFAULT_POLICY`. Callers needing a custom policy (tests, future multi-jurisdiction support) can pass a policy override via an optional parameter:
   ```ts
   export function buildTimeline(
     startedAt: number,
     totalDistance: number,
     desiredArrival: number,
     policy?: Partial<HosPolicy>
   ): Segment[]
   ```

5. The policy object design makes the algorithm directly unit-testable for edge cases without monkeypatching constants:
   - Test with `sleepDuration: 1, sleepDurationMax: 2` to isolate the cap logic with tiny values.
   - Test with `onDutyWindow: 14 * 3600` to isolate the 14-h window constraint.

6. Add comprehensive tests covering all policy boundary interactions. The existing tests continue to pass because `DEFAULT_POLICY` preserves all current constant values.

## Expected Outcome

- All current bugs (unbounded sleep, missing 14-h window) are fixed as a consequence of the policy object carrying both `sleepDurationMax` and `onDutyWindow`.
- The algorithm becomes significantly more testable: edge cases are tested by injecting minimal policy values rather than constructing artificial large distances.
- Future HOS rule additions (Canadian ELD rules, EU driving time directive, the rolling 60/70 h window if ever needed) are additive policy fields, not structural changes to `hos.ts`.
- The `HosPolicy` type is exportable from `@delivery/simulation` for use in API validation — `desiredArrival` window checks can reference `policy.sleepDurationMax` rather than a hard-coded number.
- Zero breaking changes to `buildTimeline`'s public signature when called without the optional policy parameter.

## Rationale

- **Anomaly**: The root bug is symptomatic of a deeper design issue: all HOS constants are scattered as untyped module-level `const` declarations with no cohesion. When one constant (the missing `sleepDurationMax`) is absent, there is no type system or code structure to signal the gap. The imperative `while` loop in `simulateMinimum` also has an implicit 14-h on-duty assumption baked into its control flow rather than explicitly enforced.
- **Approach**: A policy object is the standard solution to the "magic constants scattered across a file" problem. It groups related constraints, enables injection for tests, and provides a clear extension surface. This is not over-engineering: `hos.ts` already has 6 constants that interact, and the list will grow if HOS realism is incrementally improved.
- **Assumptions**: The `packages/simulation` package boundary permits internal refactoring freely; only `buildTimeline` and `HosError` are public exports. The refactor does not change the public API signature when called without the optional policy parameter.
- **Risk Level**: Radical — full rewrite of the internal algorithm structure. Higher implementation effort and a larger diff. Correctness must be demonstrated by the full existing test suite passing plus new tests. However, the externally visible contract (`buildTimeline` signature and `Segment[]` output shape) is unchanged, so callers in `generate.ts` and `seed-demo-trip.ts` require no updates.
