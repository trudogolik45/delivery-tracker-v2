# ADR-0003: Content-Addressed Storage для Upload'ов

## Status
Accepted

## Context
Dispatch Manager'ы загружают фотографии груза (jpeg/png/webp/gif, ≤10 MB). Необходима стратегия именования файлов и управления дублями.

## Decision
Файлы хранятся с ключом `{sha256(content)}.{ext}`. Директории шардируются по первым двум символам хэша (`{hash[0:2]}/{key}`). При повторной загрузке того же файла возвращается существующий `uploadId` без перезаписи (idempotent).

В БД хранится `storage_key`, а не URL. Публичный URL собирается в runtime через `storage.url(key)`, что позволяет сменить storage backend без миграции данных.

## Alternatives Considered

- **UUID-именование** — каждый upload уникален, нет дедупликации; тот же файл дважды занимает место дважды.
- **Оригинальное имя файла** — коллизии имён, потенциальные path traversal атаки, нет дедупликации.
- **UUIDv7 + отдельный хэш в БД** — сложнее: нужен SELECT по hash для дедупликации.

## Consequences

**Positive:**
- Автоматическая дедупликация: одна фотография у разных Cargo → один файл на диске.
- `Cache-Control: immutable` безопасен — содержимое по ключу никогда не меняется.
- Идемпотентность: ретрай загрузки не создаёт дубли.
- URL host-relative (`/uploads/<2char>/<key>`) — не утекает admin-домен на share-страницы.
- Абстракция `Storage` интерфейса позволяет заменить LocalStorage на S3/R2 без миграции ключей в БД.

**Negative:**
- Удаление файла требует проверки reference-counting (сейчас не реализовано — orphan cleanup отложен).
- Директория `{hash[0:2]}/` ограничивает максимум 256 поддиректорий (допустимо для локального volume).

## Trade-offs
Простота дедупликации и cache-friendly URLs важнее полного ref-counting при удалении.
