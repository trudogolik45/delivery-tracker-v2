# ADR-0002: Pre-computed Trip Timeline

## Status
Accepted

## Context
Share Pages для конечных получателей должны отображать текущее положение водителя в реальном времени. Возможны два подхода: (a) хранить фактическое местоположение (GPS), обновляя его в реальном времени, или (b) вычислить детерминированный таймлайн один раз при создании поездки и интерполировать позицию на клиенте.

## Decision
Таймлайн вычисляется **один раз** при создании Trip через HOS-симулятор и сохраняется в `trips.timeline` (JSONB). На клиенте позиция водителя интерполируется функцией `interpolate(trip, Date.now())` из `@delivery/simulation/interpolate` — без обращений к серверу.

## Alternatives Considered

- **GPS-трекинг (realtime)** — требует SDK на устройстве водителя, WebSocket/SSE канал, постоянную запись позиций в БД. Операционная сложность несоразмерна задаче трекера тяжёлых грузов с фиксированным маршрутом.
- **Server-side position polling** — периодические запросы `/trips/:hash/position`. Нет пользы перед клиентской интерполяцией, добавляет нагрузку на API.

## Consequences

**Positive:**
- API в runtime практически idle — только отдаёт JSON по hash.
- Share Page работает без WebSocket/SSE инфраструктуры.
- Детерминированность: одна и та же позиция при одном `t` у любого клиента.
- Функция `interpolate.ts` — browser-safe, тестируемая в изоляции.

**Negative:**
- Таймлайн рассчитан по усреднённой скорости (88 км/ч FMCSA), а не реальному GPS — расхождение с фактом неизбежно.
- HOS-модель упрощена: rolling 60/70h window не реализован.
- Реальные задержки (пробки, поломки) требуют ручного pause/resume через `/trips/:id/pause`.

## Trade-offs
Предсказуемость и простота инфраструктуры приоритетнее точности до минуты. Целевой продукт — «грубый трекер» для клиента, а не диспетчерская система.
